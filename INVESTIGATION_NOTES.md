# Investigation Notes

This document records the mathematical and engineering explorations carried out during development — including what did **not** work, and why. The goal is to save anyone continuing this work from re-investigating already-explored paths.

## 1. Why splitting `tree_steps` doesn't change total cost

For a `B`-bit target, splitting the halving tree into `tree_steps` levels gives `N=2^tree_steps` leaves and a remaining space `R=2^(B-tree_steps)`. The optimal cost of a hybrid BSGS search (shared M/M2/M3 table) is:

```
cost = 2·√(N·R) = 2·√(2^B) = constant, for ANY tree_steps
```

Verified numerically for B=140: `tree_steps=19,40,70,95,120` all give `cost ≈ 2^71`. This is the Shoup (1997) lower bound for generic-group DLP — it doesn't depend on how the problem is internally partitioned.

**Practical consequence**: for Puzzle #64 (B=64), cost is `2^32-33` — feasible on a personal machine (~2 min, validated). For Puzzle #140 (B=140), cost is `2^70` — even with a top-end GPU cluster, decades to millennia.

## 2. The search for a pruning predicate (branch pruning)

The following formulations were explored and refuted, with mathematical and/or empirical rigor:

- **Algebraic invariant pruning**: would require a correlation between the scalar `b` and cheap properties of the resulting EC point. This would, by definition, be a distinguisher against the hardness of ECDLP on secp256k1 — not an implementation bug.
- **Collision-density pruning / grouping leaves by `b` range**: recursively decomposes into a sub-DLP of the same type (`Q = P - b_msb·2^k·G`, search `b_low` in a range) — a proof of cost equivalence, not an absence of effort.
- **Alternative-algorithm "pruning" via a different search structure**: same equivalence — trading memory for time (or vice versa) doesn't change the underlying `N·R` product.
- **Blind MITM / streaming without materializing `leaves.bin`**: not materializing doesn't avoid having to compute; generation cost is the same either way.
- **"Climbing" the tree from a leaf (bottom-up)**: without knowing the bits removed on the way down, the number of possible ancestors DOUBLES at every level climbed — it expands exponentially, it doesn't collapse.
- **Per-level pruning filters** (a `Bloom_d` at every intermediate tree depth `d`, not just at the 45-bit leaves, motivated by the fact that node count doubles at each shallower level): a second, independent confirmation of the same conservation law. At depth `d`, a valid membership test needs to cover `2^(64-d)` remaining candidates; testing all `2^d` nodes at that depth against that space costs `2·√(2^d · 2^(64-d)) = 2·√(2^64)`, i.e. exactly `2^33` for any `d` — the same total as the full `tree_steps=19` search. The apparent exponential saving from pruning early is exactly cancelled by the exponentially larger space each intermediate node would need to be checked against.
- **Bottom-up/top-down intersection** (build an admissible set `S_45` at the leaf boundary, propagate it upward toward the root via doubling, intersect with the top-down tree at each depth): translates algebraically into exactly the same BSGS equation already used (`P - b·G = A·2^19·G`, just rearranged as `P = A·2^19·G + b·G`). A validly-constructed (zero-false-negative) bottom-up set grows to `M·2^19 = 2^50` candidates by the time it reaches the root — finding the one true intersection inside that costs the same as the BSGS search already performed. Changes the algorithm's geometry, not its information content.
- **"Birth-test" pruning at tree depth 1** (pruning immediately after the very first halving, before any deeper nodes are generated): the most favorable possible position for a cheap test, and still covered exactly by the general depth-`d` formula above — at `d=1`, `2·√(2·2^63) = 2^33`, identical to the full search. Even the earliest possible pruning point offers no discount.

### The general decision rule this converges to

Four independent formulations (leaf grouping, per-level filters, bottom-up/top-down intersection, birth-level pruning) all reduce to the same conservation law once fully specified. This motivates a standing test for any *future* pruning proposal, to apply before investing further analysis: **what new information about the scalar does this predicate use that isn't already implicit in the BSGS/Bloom search's own cost?** If the honest answer is "none" — if the predicate demands zero false negatives, no additional knowledge of `K` beyond what's already used (e.g. `--restrict-upper-half`'s puzzle-range guarantee), and operates purely on secp256k1's generic group structure — then it is, provably, moving the same `2^64` (or `2^B` in general) units of work from one place to another, not eliminating any of it.

This separates two classes of optimization going forward:
- **Legitimate** (change the real cost): restricting `A` when a real constraint exists (`--restrict-upper-half`), reducing memory footprint, improving cache/memory locality (Bloom1 tuning, blocking), tuning the Bloom hierarchy's parameters, reducing round overhead, parallelization, BSGS engineering improvements.
- **Not legitimate without new information** (redistribute the same cost): choosing `P/2` vs. `(P-G)/2` by inspection, geometric/statistical scores on the point, `x`/`y` properties, hash/CRC/entropy heuristics, per-level pruning, leaf-set pruning, bottom-up/top-down intersection.

### A precise closing statement (and a correction worth keeping)

A later re-read of the actual code (`tree_gen_leaf_at`/`tree_gen_init`) confirmed two things directly from the implementation, not just from the abstract cost argument above:

1. **The 19-level tree is not literally traversed during search.** It collapses algebraically into leaf generation (`L_b = h·(P - b·G)`, computed once per leaf); `run_hier_search` operates on the resulting flat leaf set plus a giant-step loop over `A`, with `tree_steps` only reappearing at the end to reconstruct `K`. There is no intermediate node materialized to "prune" during the search itself.
2. **The leaves have a real, confirmed linear structure**: sequential generation literally computes `L_{b+1} = L_b - E`, and combined with the giant-step decomposition, every point tested (`Q_{b,i} = L_b + i·M·G`) lies on a single scalar orbit through `P`. This is a true algebraic fact — but it is exactly the kind of structure baby-step/giant-step is built to exploit (a linear relation among candidates, expressed via group operations), not a *second*, independent source of savings on top of it.

**A necessary correction to how this was first phrased**: it is too strong to say a generic-group lower bound is "the minimum possible for any algorithm in this model," full stop — that overstates what such bounds establish. The precise claim is narrower and more defensible: *Shoup's generic-group discrete-log bound is a lower bound on algorithms restricted to group operations (addition, negation) with no side information*. It says nothing about algorithms that could exploit information genuinely outside that model — only that no such source of information has been found here, and that manipulating relations expressible purely via group operations on the *same* candidate set (however cleverly reorganized) cannot cross that boundary, because the bound's proof already accounts for every query strategy expressible that way.

**The operational test to apply to any future proposal**, kept in the precise form that emerged from this discussion: does the proposal produce a predicate `F(b)` such that `F(b)=0 ⟹ b` cannot be a solution, using information *genuinely independent* of the algebraic computation BSGS already performs? If `F` only manipulates `L_b = P - b·E` and expressions derived from it via group operations, the answer is no by construction — regardless of how the manipulation is dressed up (tree pruning, interval propagation, bottom-up/top-down intersection, or anything not yet tried). This is where the empirical dead ends (point-feature scores, hashes, residues, entropy, tangents) were already shown to behave exactly like predicates with no real discriminative power, and where any future proposal should be checked first, before further code or experiments.


### Empirical test: is there correlation between nearby scalars and "nearby" EC points?

Tested with real data generated during this session (Hamming distance between `b·G` and `(b+1)·G`, `(b+1,000,000)·G`, `(b+2^40)·G`): **zero detectable correlation**, consistent with pure randomness, confirming the absence of any exploitable signal.

### Empirical test: do the real puzzle keys have hidden structure?

Using the 65 real, official values from [OEIS A369920](https://oeis.org/A369920) (confirmed private keys for puzzles #1-65): correlation between consecutive keys of `+0.099` (only `0.79` standard errors from zero — noise, not signal). Normalized distribution consistent with uniformity. Confirms the puzzle creator's own statement ("there is no pattern, they're just consecutive keys from a deterministic wallet masked to set difficulty").

### The limit of the language: "not found" vs. "impossible"

An important distinction maintained throughout this investigation: the results above demonstrate that **the analyzed formulations do not provide a useful pruning predicate** — not that **no possible predicate could ever exist**. A genuinely new predicate, if found, would have to produce information about an entire branch without essentially solving the same cryptographic problem — which would amount to a non-trivial distinguisher for secp256k1.

## 4. Memory profiling (Puzzle #64, `m-bits=31`)

- `Bloom1` (3.9GB) dominates search time: **~94% of instrumented time**, `~786-1580ns` per check (measured with 1 and 8 threads).
- Thread scalability: `-t 1` → `-t 8` gives `5.13×` gain (`64%` parallelization efficiency) — neither pure CPU-bound nor pure memory-bound; there is real contention but also memory-parallelism headroom not yet saturated.
- Memory/compute trade-off (`m-bits`): tested `m-bits=29` (965MB, 4× less memory) — each individual check became `2.74×` faster, but the number of required giant steps grew `4×`. Net result: `2.74×` **slower** overall. `m-bits=31` confirmed as near the practical optimum.

## 5. An optimization attempt that failed in practice (documented for future reference)

Reformulated the `i2` summation using the affine-affine `AddDirect` formula (3 field multiplications) instead of the general mixed formula `add_mixed_z2eq1` (11 field multiplications), with the division deferred for batch inversion. Theoretically should have been faster. **Measured, it came out ~5% slower** (133.65s vs 127.18s). Reverted. Lesson: field-operation counts don't always predict real performance — cache behavior, compiler optimization, and other low-level effects can dominate. Always measure, never assume.

## 8. Blocked Bloom filter — isolated retry succeeded (`--bloom1-block-bits`)

**First attempt (above), reverted.** Confining all `k_hashes` positions to a single 512-bit block gave a clear regression (209.21s vs. 115.89s), traced to two compounding causes: Bloom1 itself getting crowded (~35.6 elements/512-bit block), and `bloom_positions()` being a single function shared by all three Bloom filters — accidentally blocking `Bloom2`/`Bloom3` too, which were never meant to be touched (confirmed via `Bloom2_pass/Bloom1_pass` jumping from ~3.2% to ~103%).

**Second attempt: properly isolated.** Gave `BloomFilter` its own `block_bits` field (0 = classic, persisted through save/load — an earlier version of this fix had a real correctness bug: `block_bits` wasn't written to/read from the `.bin` file, so a hierarchy built with blocking would silently search with the classic formula, causing near-total false negatives; fixed by adding it to `write_bloom`/`read_bloom` and bumping `HIER_VERSION` so old files are cleanly rejected instead of read misaligned). With this fix, `Bloom2`/`Bloom3` always use `block_bits=0` regardless of what Bloom1 is configured with.

**Block size sweep, `k=4`, isolated, against Puzzle #64 (known answer, correctness confirmed in every run):**

| Config | Search time | Bloom1-pass | vs. classic k=4 |
|---|---:|---:|---:|
| classic k=4 (baseline) | 115.89s | 2,093,995 | — |
| blocked 512B | 130.93s | 5,792,482 | −11.5% |
| **blocked 1KB** | **111.45s** | **2,150,392** | **+4.0%** |
| blocked 2KB | 149.59s | 7,212,100 | −22.5% |
| blocked 4KB | 127.62s | 4,698,299 | −9.2% |

**1KB is the winner** — a modest but genuine and reproducible ~4% gain, with false-positive selectivity nearly identical to classic (+2.7% Bloom1-pass, vs. the 2.4-2.8x blowup at 512B/2KB/4KB). Combined with the earlier `--bloom1-k 4` tuning, this gives ~14.7% total improvement over the auto-`k` baseline.

**Honestly unexplained: the result is non-monotonic in block size** (1KB best, then classic, then 4KB, 512B, 2KB in decreasing order of speed) — not a smooth curve. A pre-registered analytical simulation (Poisson occupancy model, then a direct simulation of the actual double-hashing formula) predicted 512B, 1KB, and 2KB should all show similarly small false-positive degradation relative to classic; the real measurements contradict this for 512B and especially 2KB, which showed far worse degradation than simulated, while 1KB matched the prediction closely. No confident root cause was found for this discrepancy — left as a genuine open question for anyone continuing this work, rather than a resolved mechanism. Blindly trying further sizes (8KB, etc.) was judged not worth the ~5-6 minutes per attempt given the unpredictability already observed.


Unlike every pruning idea explored above, this one holds: for a "puzzle N" target, `K` is guaranteed in `[2^(N-1), 2^N)` by the puzzles' own definition. Since `A = K >> tree_steps` and right-shifting preserves bit *values* (only moves their position), `K`'s guaranteed top bit becomes `A`'s top bit — `A` is **provably** always in the upper half of its range, for any `tree_steps`. This lets the search skip the lower half of the giant-step range entirely, with zero risk of missing the answer. Confirmed against this session's own solved Puzzle #64 key.

**Correctness vs. observed speedup are two different claims.** Tested against the known Puzzle #64 key: found the correct `K` again, but the wall-clock time barely changed, because that specific key's `A` happens to sit close to the *original* upper boundary — the "upper" search front (unaffected by the restriction) already reaches it quickly regardless. A single already-known test case can't demonstrate an average-case gain; it only demonstrates correctness.

**Rigorous average-case analysis** (analytical + Monte Carlo, `N=100,000`, `i_true ~ Uniform` over the valid range): the worst-case bound drops from `giant_count/2` to `giant_count/4` rounds. For the *expected total rounds across many runs*, the right statistic is the **ratio of means** (`E[rounds_old]/E[rounds_new] ≈ 2.0`, confirmed both analytically and by simulation), **not** the mean of per-run speedup ratios (`≈8.8` in the same simulation) — the latter is skewed by rare cases where the restricted search happens to land right next to its meeting point, and is not a meaningful description of typical benefit. The correct, defensible claim: *the expected total work across many runs, under a uniform-position assumption, is halved — not that any single run is guaranteed to run near 2× faster.*


With the search engine otherwise settled, `perf stat` was used to move from *inferring* the Bloom1 bottleneck (via our own instrumentation, ~94% of measured time) to *diagnosing* it with real hardware counters.

**Findings, in order:**

- **IPC ≈ 1.28, cache-miss rate ≈ 28%, dTLB-miss rate ≈ 98%.** The data-TLB number is the standout — virtually every Bloom1 memory access triggers a page-table walk. With `m-bits=31` (~3.9GB), the structure spans ~1,022,000 standard 4KB pages, far beyond what any real TLB can hold (~1,000-1,500 entries); with 2MB huge pages it would need only ~2,000 pages — small enough to fit.
- **Non-atomic reads.** `bloom_check()` is only ever called during the search phase, after the hierarchy is fully built and never modified again — `build_hierarchy()` only ever calls the atomic `bloom_add_atomic()`, and the two are never invoked concurrently on the same structure. Removing the unnecessary `__atomic_load_n(..., ATOMIC_RELAXED)` in favor of a plain read gave a real, measured **~2× reduction in per-check cost** (786-1580ns → ~450-540ns across repeated runs).
- **Huge pages via `madvise(MADV_HUGEPAGE)`.** Switched Bloom1's allocation from `malloc`/`calloc` to `mmap` + an explicit huge-page hint. Confirmed **active** via an in-process check (`/proc/self/smaps_rollup`, read while the process is still alive — checking `/proc/meminfo` *after* the process exits always shows 0, since anonymous memory is released on exit): ~98% of Bloom1's footprint was backed by huge pages. **Despite this, the dTLB-miss rate barely moved** (98.3% → 98.1%). Most likely explanation: WSL2/Hyper-V nested virtualization — guest-level huge pages don't guarantee the hypervisor's own second-level address translation (SLAT/EPT) also uses large pages, and `perf`'s counters may be dominated by that layer. This is outside what's controllable from inside the guest OS; results may differ on bare-metal Linux.
- **Bloom1 hash-count tuning (`--bloom1-k`).** The theoretically-optimal hash count (minimizing false-positive rate for a given size) is not the same as the wall-clock-optimal one, once the real cost of a memory access is accounted for. Sweeping `--bloom1-k` at fixed memory size (`fp-rate=1e-3`, `m-bits=31`) found a real **~10% additional speedup at `k=4`** (115.89s vs 127.99s baseline), with a "good zone" around `k=4-6` and clear degradation both above (auto, ~7-9) and below (`k=3`: −9.9%, `k=2`: −17.8%) that value. Important clarification: `k` and Bloom1's memory footprint are **independent parameters** in this implementation — `bit_count` depends only on `entries` and `fp_rate`, never on `k`; lowering `k` at fixed size trades a higher *effective* false-positive rate (more downstream ECC work in `i2`/`i3`) for fewer memory accesses per check. This is distinct from the `fp-rate` sweep in section 4, which *does* change memory size.
- **Increasing `fp-rate` directly** (which *does* shrink Bloom1) was also tested: `3e-3` gave +8.1%, but `1e-2` gave −22.7% — the `i3` subloop's share of time jumped to 36% at that point, as Bloom3 (inheriting the same nominal rate) let through enough false positives to dominate. Same shape of trade-off as the `m-bits` sweep in section 4, just tuning a different knob.
- **Sorting active-lane queries by their primary Bloom1 word before checking**, to group queries landing on the same memory page together (an average of ~33 lanes were expected to collide per huge page, by birthday-paradox reasoning, given ~65,536 lanes/thread against Bloom1's ~1,997 huge pages). **Measured 27-33% SLOWER**, not faster, and reverted. Two candidate explanations: (a) a 2MB huge page is a much coarser grain than a 64-byte cache line, so lanes sharing a page may still land on different cache lines, sharing little real benefit; (b) if the true bottleneck sits at Hyper-V's own second-level address translation (per the huge-pages finding above), grouping by guest-level page may have no correlation with what matters at the host level. Either way, the `std::sort()` cost itself (tens of thousands of elements, once per round, up to ~8,192 rounds) was a real, measured cost that the hoped-for locality gain never paid for.

All results above are single-run measurements on one specific machine (WSL2, 13GB RAM) — re-run any sweep before trusting a value on different hardware, and prefer repeated runs over single data points where the effect size is small (the `k=4/5/6` ordering itself showed non-monotonic noise between single runs, even though the broader "good zone vs. degradation outside it" trend was clear and reproducible).

## 9a. First-round memory warm-up cost — a real, measured acceleration win

Following the "A-space optimizer" discussion (measure, don't theorize further), a `--dump-round-stats` mode was added to log per-64-round deltas of every pipeline stage's time and operation counts, purely observationally.

**Finding**: the first 64-round window of a real search cost 66.67s wall-clock, while every subsequent 64-round window cost a stable ~10.7-11.1s — a one-time ~56s anomaly that never recurred. Suspected cause: even though huge pages were confirmed active at the guest (WSL2) level immediately after loading (via the existing `/proc/self/smaps_rollup` check), the underlying host (Hyper-V) may commit physical memory lazily on first real touch — so the first full pass through Bloom1's ~3.9GB pays a page-fault-like cost region by region, then never again.

**Fix tested**: touch one word per 4KB page across Bloom1/2/3, in parallel, right before starting the timed search (moving any one-time cost out of the measured search time rather than trying to eliminate the underlying cause, which isn't controllable from inside the guest OS).

**Result**: the anomaly dropped from 66.67s to 23.95s (a 64.1% reduction) at a pre-warm cost of only 3.48s — a confirmed net gain of ~39.2s, the single largest win of this whole optimization phase. The anomaly wasn't fully eliminated (23.95s vs. the ~11s steady-state, still ~2.2× higher) — a more thorough touch (every cache line instead of once per 4KB page) might close more of the gap, but was judged not worth pursuing: an 8× more expensive touch has to compensate for only ~13s of remaining anomaly, an uncertain trade not chased further here.

## 9b. Radix-4/5-level hierarchy — real gain, poor cost-effectiveness (not adopted)

Tested replacing the classic 2-level radix-32 hierarchy (`i2`×`i3`, `Bloom2`/`Bloom3`) with a 5-level radix-4 alternative (4 intermediate Bloom filters + exact table, `4^4=256` combined with a larger exact table to reach the same `1024`-way total granularity), motivated by the theory that fewer, cheaper per-level checks (~4 expected vs. ~33 in the classic scheme) might outweigh the extra intermediate memory needed (each level represents a much larger absolute candidate range at smaller radix).

**A real correctness bug was found and fixed during validation**: the exact table was initially sized for `M/1024` entries, but 4 levels of radix-4 branching only produce `4^4=256` combinations, covering just `M/256` — the exact table was 1/4 the size it needed to be, causing genuine false negatives (confirmed directly: the search passed round 640 without finding Puzzle #64's known answer, which classic mode finds reliably by round ~574-576 using the identical outer search loop — same instance, so this had to be a bug in the new lookup function, not misfortune). Fixed by sizing the exact table to `level_M[3]` (`M/256`) instead, matching the space actually narrowed down to by the 4 Bloom levels.

**After the fix, correctness confirmed** — found `K` at round 576, matching classic mode's result for this key exactly. **Performance: ~5.1% faster** (106.05s vs. ~111.5s reference), with internal operation counts dropping dramatically as predicted (~10× fewer `Add()`, ~8× fewer level-1 Bloom passes) — but at a cost of **~1.3GB of additional intermediate memory** (11.4× more than the classic scheme's Bloom2+Bloom3, ~124MB) and ~20% slower hierarchy construction (~287s vs. ~240s). Every other optimization retained in the main binary (`bloom1-k`, `bloom1-block-bits`, pre-warming) costs zero additional memory; this is the only one that doesn't, and it has the smallest gain-per-cost ratio of the whole session. **Not adopted** — kept as a validated experimental result, not promoted into the default build. (Note: the printed per-stage time breakdown for this mode is currently misleading — only the initial Bloom1 check has its own timer; levels 1-4 and the exact table reuse the existing *operation counters* but not the *timers*, so all measured time appears attributed to "Bloom1 check" even though real work happens throughout the descent. The overall search-time comparison above is unaffected by this — it's an end-to-end wall-clock measurement — but the internal breakdown would need its own timers added before trusting it for further diagnosis.)

**Radix-2 (binary halving, 10 levels) modeled — not implemented.** Extending the same cost model that correctly predicted radix-4's memory requirement: a `1024`-way binary hierarchy would need **~3.85GB of additional intermediate memory** (3× more than radix-4, nearly matching Bloom1's own 3.86GB) to reduce expected checks per Bloom1-pass from ~4 to only ~2 — half, not another order of magnitude. This confirms a clear, monotonic trend across all three data points now available (radix-32 → radix-4 → radix-2 modeled): each further reduction in branching factor yields diminishing returns in checks saved while memory cost keeps growing, in the wrong direction given this session's memory-is-the-real-bottleneck finding. Not worth an implementation-and-debug cycle to confirm empirically what the validated radix-4 model already predicts clearly.

**Family closed: tree-halving / radix subdivision (CLOSED).** Successive subdivision reduces *local* branching factor but never reduces the underlying mathematical candidate set — the same conclusion as every structural-pruning line in section 10, arrived at here independently via a cost-engineering lens rather than an information-theoretic one. `radix-4` already crossed the practical optimum within this family; deepening further is counterproductive. Two productive directions remain open: (1) continuing to optimize the existing radix-32 path itself (memory/TLB/prefetch/locality/NUMA/Bloom layout/pipeline — where this session's real wins have consistently come from), and (2) genuine pruning, only if a new source of information about the scalar or instance-generation process is ever found (per section 10's admission rule) — not from further reorganizing the same search geometry.

## 9c. History-based adaptive pruning (CLOSED) — and a refined admission test

A further batch of seven "history-based" pruning proposals was evaluated (negative certificates per subtree, necessary-signature filters, negative-state caching, exhausted-block certificates, sibling-killing, inverse-Bloom-by-region, and miss-density-adaptive tree shape). Applying the section-10 rule precisely to each:

- **Negative certificates / necessary signatures / inverse-Bloom-by-region**: when fully specified, each is algebraically identical to the existing Bloom1/2/3 mechanism (an OR-of-hashed-features summary over a candidate set *is* a Bloom filter; its "saturation" concern is the same size/false-positive trade-off already explored via `bloom1-k` and block sizing) — not new information, just a redescription of what's already implemented.
- **Negative-state caching**: doesn't apply to this specific search — intermediate states are distinct elliptic-curve points from an order-~2²⁵⁶ group, so genuine state collisions between different (leaf, round) pairs have probability ~1/n, unlike graph-search problems with real shared substructure to amortize over.
- **Exhausted-block certificates / sibling-killing**: both explicitly require the same undiscovered hereditary predicate from section 10 (the proposer's own analysis for sibling-killing concedes "normally, no" for generic ECDLP).
- **Miss-density-adaptive tree**: collapses into sibling-killing (if branch compression skips testing candidates based on other branches' outcomes — the same risk of silently discarding the true answer already demonstrated by simulation) or into harmless reorganization with no reduction in total candidates tested (the same category as the closed radix family).

**A useful refinement to the admission rule**, worth keeping alongside section 10's: a candidate certificate/summary being "just another representation of the same target set" is not automatically disqualifying by itself — what matters is whether it encodes a **genuinely new constraint on the scalar space**, not merely a repackaging of the identical candidate set already indexed by Bloom1/2/3. No proposal examined in this session has cleared that bar.

**Family closed: history-based adaptive pruning (CLOSED).**

## 9d. The clean boundary for any future work

Restated at its most operational: **no new information → optimize BSGS. New information → look for pruning.** Three classes of genuinely new information were identified as still theoretically open (not yet ruled out by any proof in this document, unlike everything above):

1. **Puzzle construction restrictions beyond the known bit-length interval** — tested empirically in this session (OEIS A369920, all 65 known keys: correlation between consecutive keys `+0.099`, ~0.79 standard errors from zero — noise; uniform distribution confirmed). No signal found, but remains open if the puzzle creator or community ever reveals more about the generation method.
2. **Relations between multiple instances** — tested in the same analysis; would have shown up as the same correlation if present. Doesn't apply to Puzzle #64 regardless, since it's already solved.
3. **An externally verifiable structure of the target set that constrains the scalar space itself** (not merely another encoding of the same candidates) — genuinely open, no known candidate.

If none of these three ever materializes, the search for mathematical pruning is complete for this problem. Remaining productive work is bounded and concrete: compacting hot-path data structures for cache-line density (the exact table is a reasonable low-risk candidate, though it touches only ~0.03% of total operations — a small ceiling on the possible gain), and the still-pending `perf stat` run with pre-warming active, to characterize the ~13s residual anomaly identified in section 9a.

## 9e. Dynamic MITM reconstruction on the upper side (CLOSED)

A further proposal suggested reconstructing the upper-side MITM candidate set after each round from survivors, rather than enumerating it upfront — distinguishing "lazy reconstruction" (same information, just deferred) from a genuine narrowing if a round's outcome could impose a new constraint on which states remain possible. Three independent refutations, evaluated precisely against this codebase rather than in the abstract:

1. **No useful DAG/convergence between candidates.** The precise statement matters here, not just "prime order": for a generator `G` of prime order `n`, `aG ≡ bG (mod n)` implies `a ≡ b (mod n)` — so within a scalar interval far smaller than `n` (as every interval in this problem is), distinct scalars always produce distinct points. It's this combination — prime order *and* an interval much smaller than `n` — that rules out convergence, not primality alone (which says nothing about an arbitrary subset of scalars by itself). Applied here: each of the 524,288 leaves follows its own distinct trajectory through giant-step space; no two ever reach the same intermediate state to merge.
2. **Predecessor cardinality gives no compression.** Backward-reconstructing predecessors of a surviving state, under the upper-half constraint plus the previous round's transformation, yields exactly the cardinality already predicted by the BSGS decomposition — a miss at one position is information about that one candidate/state, not about the others. No narrowing beyond what BSGS already provides.
3. **The implementation has no shrinking survivor set to reconstruct from.** `active[]` stays at 524,288 constant until the final round (established directly from the code early in this session), where all lanes drop simultaneously except the one that hits. The assumed dynamic `S_0 ⊃ S_1 ⊃ S_2 ⊃ ...` simply doesn't exist in the real search loop.

**Family closed: dynamic MITM reconstruction (CLOSED).** No useful DAG exists between distinct candidates; predecessor cardinality offers no reduction beyond the BSGS decomposition; and the current implementation has no `active[]` set that shrinks between rounds. Dynamic reconstruction is therefore only a reparameterization/lazy generation, not additional pruning.

## 9f. Birth-time interval pruning in the halving tree (CLOSED — structural proof)

A distinct and well-posed variant: at each halving step, before materializing both children `Q0=Q/2` and `Q1=(Q-G)/2`, check whether each child's *implied scalar interval* is still consistent with the known constraint `K∈[2^(N-1),2^N)`. If one child's interval falls entirely outside the valid range, prune it at birth without ever generating it — genuinely different from every prior "reconstruct leaves" variant, since the test here is about interval membership, not about test outcomes from other candidates.

**Computed directly for Puzzle #64's actual parameters** (root_bits=64, 19 halving levels): propagating `[2^63, 2^64)` through all 19 levels, checking at each level whether the even-child or odd-child interval becomes empty — **neither ever does, at any of the 19 levels**. Both children remain viable throughout.

**The reason is structural, not a coincidence of this puzzle**: `[2^(N-1), 2^N)` is a *complete dyadic interval* — it starts exactly at a power of 2 and spans exactly one power of 2. Such an interval always contains exactly as many even values as odd values, and this property is preserved recursively: each child's resulting interval is again a complete (or effectively complete) dyadic interval at the next level down. Since every Bitcoin puzzle in this series uses exactly this `[2^(N-1),2^N)` form, this result isn't specific to Puzzle #64 — it holds for the whole family by construction.

**What this means concretely**: the *only* new information the known interval constraint could contribute is already fully captured by `--restrict-upper-half` (restricting the top-level `A` search to its upper half) — propagating the same constraint level-by-level through the halving tree doesn't yield any additional pruning, because the interval's own dyadic shape spends that information entirely in one decision at the top, leaving nothing further to extract at deeper levels.

**Family closed: birth-time interval pruning (CLOSED)** — with a structural proof specific to this variant, distinct from (though consistent with) every other closure in this document.

## 9g. Point-intersection variants in the tree (CLOSED — two distinct reasons)

Four readings of "intersecting points in the tree" were distinguished and evaluated:

1. **Branch ↔ branch** (do sibling subtrees' points ever coincide?): closed by the same prime-order argument as section 9e — for a generator of prime order `n`, `xG=yG ⟹ x≡y (mod n)`, and within any scalar interval far smaller than `n` (as every interval here is), distinct scalars always give distinct points.
2. **Tree ↔ MITM candidate set** (does `L_b` intersect the target set?): this *is* the search's own success condition (`L_b = A·G ⟺ K = A·2^s+b`), not an independent pruning mechanism — restating the goal isn't a new technique.
3. **Descendants ↔ descendants** (do two branches' descendant sets overlap?): closed by the same argument as (1) — no convergence is possible.
4. **`φ(subtree) ∩ φ(admissible MITM) = ∅`** as a cheap certificate, using auxiliary images of scalar *intervals* rather than individual points: this is the same over-approximation question from the "out-of-the-box" batch (compressing a whole interval's image into a small set cheaply, without enumeration). Closed by a **different** argument than (1)/(3): such a `φ` would need to be a sound (no false negatives) compression of an interval's point-set computable without enumerating it — exactly the kind of algebraic compressibility between exponent and point coordinates whose *absence* is what makes ECDLP hard on this curve. Not covered by the generic-group (Shoup) bound used elsewhere in this document — covered instead by secp256k1's specific, extensively-scrutinized cryptographic hardness assumption.

**Two distinct closing reasons, not one** — worth keeping separate for any future proposal: readings (1)-(3) fail because of prime-order injectivity within a small interval (a proven, unconditional fact about this group); reading (4) fails because it would require breaking a hardness assumption (an empirical, not proof-based, closure — the strongest kind of "no known way," but not a theorem). Any future point-intersection proposal should be checked against whichever of the two categories it actually falls into.

## 9h. Transition-graph pruning (CLOSED — direct proof)

A cleaner framing than testing individual point properties: instead of asking "which child is valid at each node," ask whether entire **sequences** of halving decisions (bit patterns) can be proven impossible for `K∈[2^63,2^64)`. If some subset of `{0,1}^19` sequences were provably unreachable, whole subtrees could be pruned by pattern alone.

**Proven directly, no simulation needed**: the sequence of 19 halving decisions *is*, bit for bit, the low 19 bits of `K` — each step's chosen parity is exactly the current least-significant bit of `K` before it's shifted right. The interval constraint `K∈[2^63,2^64)` fixes only bit 63 of `K`; bits 0-18 are structurally independent of bit 63 in any binary representation — any 19-bit pattern can be paired with bit 63=1 to form a valid `K` in range. **All `2^19` sequences are therefore possible**, for this puzzle and for every puzzle in this series (the argument depends only on which single bit the interval constraint fixes, not on this specific `K`).

**Family closed: transition-graph pruning (CLOSED)** for the plain interval constraint — matching the proposer's own prediction, now proven rather than merely suspected. Would only reopen for a constraint that ties high and low bits together (e.g. a modular relation spanning both), which is exactly the same external-information requirement as the remaining open classes in section 9d — not a new mechanism to pursue with the information available now.

## 9i. The unifying meta-theorem behind every MITM/recursion closure

Across many sessions of proposals — MITM-of-MITM, MITM-half, centered MITM, recursive radix subdivision, negation/GLV as pruning, `R=AG+bE` and its algebraic variants, multi-target BSGS on the arithmetic-progression leaves, the halving-operator composition (`H_{b1}(H_{b0}(P))`, proven to reveal genuine shared midpoints that nonetheless don't reduce total work — see the `Q9` result below), 3-way MITM, distinguished points/Pollard rho, bit-reversal MITM, difference-based MITM, multi-scale branch-and-bound, injective fingerprints, and finally recursive MITM with reusable certificates — every single variant closes for the same underlying reason, however differently each was phrased.

**The principle**: Shoup's generic-group lower bound is a statement about the total information extractable from group operations about a `(candidate, exponent)` pair, given `N·R` hypotheses to distinguish — not a statement about any particular algorithm's structure. It is therefore invariant under reorganization: computing everything at once, splitting into levels, reusing intermediate results, composing certificates into a DAG, or recursing arbitrarily deep all remain bounded below by the same `2√(N·R)`. No accounting trick — deferring cost, amortizing it across levels, or declaring one stage's output "reusable" for another — changes the total information-theoretic requirement, because the bound was never about *where* the cost appears in a computation graph, only about how much there necessarily *is*.

**Practical corollary for any future proposal in this family**: before attempting a new formulation, check whether it changes `N` or `R` themselves (the only way to actually reduce `2√(N·R)`) versus merely reorganizing, deferring, or relabeling the same computation. Sections 9b, 9c, 9e, 9g, and 9h each independently rediscovered this same fact from a different angle — worth recognizing as one theorem rather than five, going forward. "Lateral movement" between states (`L_b ↔ L_{b+Δ}`, or simultaneous shifts `A→A+Δ_A`, `b→b+Δ_b`) is a further independent rediscovery, this time via a spatial/directional framing rather than a computational-reorganization one: any simultaneous lateral shift consistent with the same underlying equation is forced into the linear relation `Δ_A + c·Δ_b ≡ 0 (mod n)` (verified directly) — confirming no second free dimension exists to exploit, and that direction of traversal (vertical, horizontal, diagonal) is as irrelevant as computational reorganization — only a genuine zero-solutions exclusion certificate would matter, and none is known. Batch-and-reconstruct MITM (`S_0 → S_1 → S_2` via per-batch surviving subsets, rather than explicit recursive certificates) was recognized as the identical condition in different notation the moment it was framed with the "genuine reduction, not just already-tested exclusion" requirement made explicit — the meta-theorem applies without needing a fresh proof, a useful check that it generalizes correctly across surface-level rewordings. A concrete instance worth keeping on record: composing the halving operator as `H_{b1}(H_{b0}(P))` (splitting `b`'s 19 bits into a 9-bit prefix and 10-bit suffix) was *proven* — not merely argued — to produce genuine shared intermediate points (512 distinct `Q9` values, each shared by exactly 1024 leaves), yet this true structural fact still yields no savings: it costs slightly *more* than direct generation (524,800 vs. 524,288 point operations) and, more fundamentally, the shared `Q9` is consumed entirely within generation, which the search phase (Bloom1/2/3, ~99% of total time) never touches — a clean illustration of the meta-theorem: real structure can exist without being exploitable, when it lives on the wrong side of the `N·R` accounting.

## 9j. General impossibility of a hereditary parent→descendants predicate

Section 9f showed one specific hereditary predicate (interval membership) never fires, for the specific dyadic interval `[2^63,2^64)`. This section proves something stronger: **no** cheap, non-trivial hereditary predicate `F` (any `F` with `F(v)=impossible ⟹ F(descendant)=impossible ∀ descendants`, computable without doing work equivalent to exploring those descendants) can exist for this tree at all, given the standing premise of section 9d (no information about `K` beyond the known interval).

**The argument**: accepting that premise means `K` is uniform over its admissible interval, and section 9f's dyadic-completeness proof extends directly to show all `2^19` prefixes of `b` are equally likely a priori — the true prefix is statistically indistinguishable, ahead of time, from any other prefix at the same depth. A predicate `F(v)` can only depend on `v`'s own identity (its point `Q_i`, or the prefix generating it) — never on `K_true`, which is exactly what's unknown. By this uniformity, the node lying on the true path is a priori indistinguishable from any sibling node at the same level: any point `Q_i` is an equally valid, equally likely elliptic-curve point regardless of whether its generating prefix matches `b_true`'s. Therefore, if `F` ever classifies some node as impossible, by symmetry it has exactly the same chance of doing so incorrectly on the true node — unless `F` uses information that algebraically distinguishes the correct point from incorrect ones, which reduces to the same distinguisher-against-secp256k1 argument already refused in section 9g point 4.

**Family closed: hereditary parent→descendants pruning (CLOSED), in full generality** — not merely "no known candidate," but structurally impossible under the accepted premise, via statistical indistinguishability rather than a case-by-case check of specific predicates. This subsumes section 9f as one instance of a general theorem rather than a standalone result. A BST-pruning framing (searching for a monotonic `F(Q)` whose ordering, like a BST key, lets a local comparison eliminate an entire subtree) was also checked directly against a data-structures reference page and confirmed to add nothing new: BST pruning works only because insertion actively *imposes* key ordering on the tree's shape — our halving tree's shape comes from cryptographic operations with no such imposed order, so any monotonic `F` is just another instance of the hereditary predicate already ruled out above.

A related framing — building a prefix tree directly on `K`'s MSBs (`K=1p_1p_2...`, testing whether a whole prefix interval `I_p=[p·2^r,(p+1)·2^r)` can be excluded cheaper than searching it) — was checked numerically against the block-certificate cost already established, correcting for the exact bit-scale relationship between `K`'s prefix length `r` and the corresponding `A`-space slice `Δ_A=R/2^r`: the certificate is never cheaper than the marginal cost of searching that slice within the existing optimal architecture, and the gap widens sharply with `r` (2× worse at `r=2` bits, 32× at `r=10`, over 700× at `r=19`, growing to millions-fold for larger `r`). This is the same block-certificate question from earlier in the investigation, reindexed onto `K`'s bits instead of `A`'s — not a new mechanism, now confirmed numerically in this specific framing too.






The general principle this whole investigation converges to, stated at its most precise: **new structural pruning ⟹ new information**. Given the information model currently available to AMALIA — `I = {P, G, n, K's known interval, known restrictions}` — the interval is already incorporated (`--restrict-upper-half`); every other transformation examined (`P`, `x(P)`, `y(P)`, `P/2^s`, `φ(P)`, `R-A·M·G`, and every block/sequence-level variant built from them) is a function of elements already in `I`. Looking for another pruning mechanism from these alone means searching for a distinction the problem itself doesn't supply.

**This is a precise claim, not a universal one.** It does not prove no conceivable ECDLP pruning could ever exist. It proves something narrower and more useful: *within the information model currently available to AMALIA, no identified source of additional information supports constructing a structural pruning mechanism.* If a genuinely new source of information about a specific instance's generation process ever surfaces (not extractable from `P` itself, but documented or otherwise verified about how a particular `K` was produced), that would be the trigger to reopen this — and it would slot in exactly like `--restrict-upper-half` did, not as another point-feature or block-property search.

**The operational rule for any future proposal**, to apply before any implementation:

```
New idea
   │
   ├── does it introduce genuinely new information (not derivable
   │   from P, G, n, and quantities already in the search)?
   │       │
   │       └── no → do not investigate as pruning; it is at best
   │                a candidate for the acceleration category
   │
   └── yes
          │
          ▼
      can it actually eliminate part of the search space for K?
          │
          ├── no → optimization (may still be worth pursuing on its
          │        own merits, e.g. memory/cache/parallelism)
          │
          └── yes
                 │
                 ▼
          is its cost less than testing the candidates it would remove?
                 │
                 ├── no → discard
                 └── yes → worth a prototype
```

Structural pruning investigation for AMALIA is closed on this basis. Any future gain that doesn't introduce new information in this sense should be classified correctly as **acceleration**, not pruning — which is exactly where the project's remaining productive work lies: profiling, memory/cache locality, batching, parallelism, point arithmetic, and the `Bloom1 → i2 → i3` pipeline documented in sections 6-8 above.


Two more formulations were checked after section 2's four, closing the same boundary from further angles:

- **MITM/BSGS decomposition of `b`** (splitting the 19 tree steps, or `b` itself, into two or more coordinates and cross-matching): the non-trivial version is, by the proposer's own analysis, exactly BSGS restated. But there is a second, independent reason it doesn't matter even if it worked: `b`'s direct generation already costs ~0.53s out of ~115.89s total (~0.46%) — the theoretical ceiling on any improvement here, regardless of the decomposition's sophistication, is under 1% of total time. The bottleneck is entirely on the `A` side.
- **Grouping/testing blocks of giant-steps against the `M`-candidate table** (an attempt to prune a whole range of `A` before paying for individual `Bloom1` checks): computed directly — a valid MITM sub-search over a block of `Δ` giant-steps costs at least `√(Δ·M)`, which *exceeds* the cost of testing those `Δ` positions individually (`O(Δ)`) for every block size up to the full `giant_count=16384` (≈362× worse at that size). This is because `M` is already sized at the Shoup-optimal point (`M=√(N·R)`) for the two-level split already in place; introducing a third decomposition layer against the same table can only match or exceed that optimum, never beat it.

### The admission rule for any future pruning proposal

Six independent formulations — leaf-set pruning, per-level filters, bottom-up/top-down intersection, birth-level pruning, `b`-side MITM, and giant-step block grouping — all reduce to the same structural fact: *same information + same table + same search space ⟹ reorganization, not pruning*. Before writing any code for a new idea, require it to answer three questions, in order, and stop if any fails:

1. **What new information** does the predicate use, beyond `P`, `G`, and quantities already derivable from the existing `A`/`b` search (i.e., beyond what the current Bloom/BSGS machinery already computes)?
2. **At what level does it act**, and against what existing structure — does it act *before* `Bloom1` in a way that could actually skip that cost, or does it act on an already-cheap dimension (like `b`) where even a perfect result is capped at negligible impact?
3. **Does it satisfy both a cost condition and an information condition simultaneously**: `C_prune(Δ) < C_Bloom(Δ)` for the block size `Δ` it targets, **and** `Pr[reject a block containing the answer] ≪ Pr[reject a block not containing it]`? A predicate that is cheap but non-discriminating (~50/50 between correct and incorrect blocks) doesn't prune; a predicate that is discriminating but costs more than the `Δ` Bloom checks it replaces doesn't help either. Both conditions are necessary; neither alone is sufficient.

If a proposal can't answer all three concretely, it is very likely another reparametrization of the same `N·R` conservation already established — decline the implementation, not just the optimism.

## 10. Repeat-run branch pruning (`--unsafe-prune`) — proven unsafe, implemented anyway at explicit user request

A distinct proposal from the structural-pruning family above: exclude any `b` whose bit sequence contains `n` consecutive identical bits anywhere, on the theory that such runs are "less random" and less likely for a real secp256k1-derived scalar. Tested directly with `--repeat-test` (exhaustive scan of all `2^levels` possible `b` values) before any implementation, per the standing discipline of this project.

**Result: the rule has no discriminating power** — b=0 (all-zero) is excluded, yet this codebase already generates and searches it with no special handling, and there is no evidence any real secp256k1 scalar avoids short bit-runs at a rate different from a uniform random string. Exhaustive exclusion rates at `levels=19` (Puzzle #64's `tree_steps`):

| `n` | excluded | | `n` | excluded |
|---|---:|---|---|---:|
| 3 | ~100% (76-bit prefix, `levels=95`) | | 8 | 5.1% |
| 4 | 74.8% | | 9 | 2.3% |
| 5 | 43.8% | | 10 | 1.1% |
| 6 | 22.4% | | 15 | 0.02% |
| 7 | 10.8% | | 18 | 0.001% |

The rate roughly halves per unit increase in `n` (fewer valid windows in a fixed-length string), converging to a residual floor (only the two all-uniform values `0` and `2^levels-1`) as `n→levels`, never reaching zero for `n<levels`.

**At `tree_steps=95` (Puzzle #140), the same rule is far more dangerous and far less useful simultaneously** — estimated by sampling (exhaustive scan infeasible at this size): `n=4` excludes ~99.95%, `n=7` ~52%, `n=10` ~8%, `n=15` ~0.27%. Applied to the total-cost formula `2√(N·R)`, even the most aggressive setting (`n=4`) only buys a ~44.7× reduction — nowhere near enough to make `2^71` operations tractable — while accepting a ~99.95% chance of silently discarding the correct answer. This is the general pattern: at longer `b`, an *n*-run of any fixed small size becomes near-certain somewhere in the string, so aggressive pruning here excludes almost everything, and conservative pruning excludes almost nothing — the rule gets *strictly worse* as the exact scenario it might help with (very large `tree_steps`) grows.

**Implemented anyway** (`--unsafe-prune`, `--prune-repeat-n N`), at the user's explicit, informed request, after the exhaustive-scan proof was shown and understood. Applied at leaf-generation time in both `--attack-loop` and `--block-search`. The flag name itself is the only safety signal left in the tool (all narrative warnings were removed from output at a later explicit request) — the risk is fully documented here instead. A real, reproducible correctness bug was found and fixed during this work: the pruning check originally tested the *local* leaf index within a batch/block rather than the *global* `b` (`block_offset + local_index`) — meaning every batch after the first (or any `--start-b` > 0) checked the wrong bits entirely. Confirmed by a targeted test (`n=6`, `batch_size=1024`, comparing block #1 vs block #2's survivor counts against an independent exhaustive check) before and after the fix.

**A genuine, correct, zero-risk optimization was found alongside the unsafe one**: since the exclusion rule only depends on `b`'s bits, and a *block* of `2^k` consecutive `b` values shares a fixed high-bit prefix (only the low `k` bits vary), if that fixed prefix *alone* already contains an `n`-run, the **entire block** is excluded with certainty — provable without generating a single leaf. Implemented as `block_fully_excluded_jump()`: finds the largest safe power-of-2 jump (checking alignment carefully — a window justifies exclusion only for levels `j≤i` where `i` is the window's own start position, and the block must actually be aligned to `2^j` for that claim to hold for the *whole* jump range, not just the current position) and advances `block_offset` by that many blocks in one step, entirely skipping leaf generation and search for the excluded range. Measured directly at `tree_steps=95`, `--prune-repeat-n=3`: ~30 million blocks/second skipped this way — confirmed correct (not a hang) via a live progress display, and cross-checked against the closed-form claim that all offsets sharing an all-zero high-bit prefix near `offset=0` are excluded by construction (the observed jump size, `2^60`-capped, matched the predicted `2^73`-sized excludable region exactly, accounting for the cap). This optimization changes *when* work happens, never *what counts as a valid answer* — it is safe regardless of whether `--unsafe-prune` itself is trusted.

## 11. `--block-search`: subdividing an intractable range into resumable, independently-prunable blocks

For `tree_steps` large enough that `N` (leaf count) cannot fit in memory or be generated in reasonable time as one batch (Puzzle #140's `tree_steps=95` gives `N=2^95`), the practical approach is to divide `[0,2^tree_steps)` into fixed-size blocks (matching `--attack-loop`'s existing batch size), process each with a full BSGS bidirectional search, and advance to the next block on a miss — indefinitely, or until `--max-batches`.

**A real overflow bug was found and fixed**: the block offset was tracked as `uint64_t`, sufficient for `tree_steps≤64`, but Puzzle #140's `tree_steps=95` needs up to 95 bits. Fixed by switching the block offset (and the full-`b` reconstruction on a hit) to `Int` (the codebase's existing arbitrary-precision type) — while keeping the *local* per-block generation loop on `uint64_t` (safe, since `batch_size` itself is always small). Validated by re-running the Puzzle #64 block-search test (`batch_size=1024`, answer at block #69) and confirming the correct block and full `b` reconstruction.

`--rounds-per-block N` optionally caps each block's search at `N` rounds instead of the full `giant_count/2` before moving on — useful for cycling through many blocks quickly, but **introduces a second, independent incompleteness dimension**: if the true `A` for a block that does contain the true `b` requires more than `N` rounds to reach (from either front), and blocks are never revisited, the answer is lost exactly as unsafe-pruning loses it, just along the giant-step axis instead of the `b`-axis. Not enabled by default; documented here so future use understands the tradeoff explicitly, matching the framing already established for `--unsafe-prune`.


## 12. Distributed computing (`--master`/`--worker`) and the standalone `amalia_worker` binary

Given this project's per-machine ceiling, the next axis worth exploring honestly is horizontal scaling — many machines instead of one. Implemented as a `--master` coordinator (hands out b-space blocks, collects results, never searches anything itself) and any number of `--worker` processes, each running BSGS (CPU or, later, GPU) on its assigned block, then asking for the next.

**Protocol choice**: a deliberately simple line-based text protocol over raw TCP, not HTTP. Considered and rejected implementing real HTTP - the protocol needs exactly three request types (`WORK`, `RESULT`, `GETFILE`) with no routing, headers, or content negotiation, so a minimal parser is both less code and less risk than a real (if minimal) HTTP implementation, while remaining fully testable by hand with `nc HOST PORT`. Validated in isolation first (`--net-selftest`: a listener and a client thread exchange one line locally, round-trip verified) before building `--master`/`--worker` on top of it - same discipline as every other new mechanism in this codebase.

**Real bugs found during this work, each only visible once multiple machines/threads were genuinely exercised together** (no single-machine test could have exposed any of them):

1. **`--attack-loop`'s sequential mode had no fully-excluded-block skip.** `--block-search` got the `block_fully_excluded_jump` optimization (section 10) when it was built; plain `--attack-loop` did not. Confirmed directly: an `--unsafe-prune` run at `tree_steps=95` showed `Batch #1/#2/#3: 0 leaves generated`, repeating with no visible progress - not a hang (confirmed via `ps aux`: genuine, low but real CPU use), but a sequential crawl through billions of individually-empty blocks with no jump. Fixed by porting the identical Int-based jump logic to the sequential cursor inside `--attack-loop` itself.

2. **The master's single-threaded, sequential accept-handle-close loop.** Before `GETFILE` existed this was merely inelegant (each `WORK`/`RESULT` exchange is sub-millisecond, so sequential handling was never actually a bottleneck) - but a `GETFILE` transfer of a multi-GB table can take tens of seconds to minutes, and the original loop handled one connection fully before accepting the next, meaning a single worker downloading a table would block *every other worker's* `WORK`/`RESULT` for the whole transfer. Fixed by spawning a detached thread per accepted connection, with the existing mutex narrowed to protect only the brief `WORK`/`RESULT` critical section - file transfers now run entirely outside any lock, genuinely concurrent with other workers' block requests.

3. **The dependency-extraction for the standalone `amalia_worker` binary (see below) initially missed four required symbols** - three bare `#define` constants (`DEFAULT_BLOOM_FP_RATE`, the `HIER_MAGIC*` trio, `EC_ORDER_HEX`) that live outside any function body and were consequently invisible to a function/struct-body-based dependency scan, and one entire function (`net_download_file`) dropped by a plain off-by-one/range-skip error while assembling the trimmed source. Both root causes were fixed in the extraction methodology itself, not just patched in the output: the automated closure computation was extended to also scan for bare `#define` identifiers referenced anywhere in the needed functions' bodies (re-run against the corrected file: zero further misses, independently confirmed), and the block list was re-verified against the original file's line ranges directly rather than trusted by inspection.

**Design choice worth recording**: `--master` never searches anything and never even needs to *load* the hierarchy/table files it serves - it only needs their byte size and a file handle to stream from. This was a deliberate simplification once the file-serving feature was added (an earlier version would have had the master load both tables just like a worker, for no functional reason).

**Result confidentiality**: the found `K` is reported by a worker to the master over `RESULT ... FOUND <K>` (necessarily - the master needs it to know the search is over and to display it), but is never printed to a worker's own console/log (`*** FOUND *** (result withheld from worker log - see master)`). This matters specifically for the "workers across the internet" use case this section's binary is built for: a worker machine (potentially operated by someone else, on hardware not fully trusted) does the *computation* but is not shown the *answer* it computed.

**The standalone `amalia_worker` binary**: built from a separate source file (`amalia_worker.cpp`), produced by automated transitive-dependency extraction from `run_worker` and `process_one_block_race` (starting seeds), rather than manually copying code by hand. Methodology: parse every top-level `static`/`struct`/`int main` declaration in the full source into a (name, line-range) table, extract each one's approximate body as the span up to the next top-level declaration, then iteratively expand a "needed" set by regex-searching each already-needed body for word-boundary matches against every other known symbol name, until reaching a fixed point. This is deliberately a superset-safe heuristic (a body-boundary approximation can accidentally include a neighboring declaration's leading doc-comment, and comments mentioning an unrelated function by name produce false positives - both confirmed to happen in practice, see bug 3 above) - false inclusions cost a little binary size, false *exclusions* cost a compile error, so the asymmetry is worth erring toward inclusion.

Built statically (`-static -fopenmp`) specifically so a worker machine needs nothing but the single binary - no matching glibc/libstdc++/libgomp version, no build toolchain. Confirmed via `file`/`ldd` (`"not a dynamic executable"`) and an end-to-end run against a real `--master` (Puzzle #64, both directly and via a from-scratch download of both table files into an empty directory - both scenarios found the correct, already-known `K` in the same block and round as every prior validated run). One caveat surfaced directly at build time (a linker warning, not a runtime failure): glibc's static NSS modules do not reliably resolve hostnames via `getaddrinfo()` when statically linked - `--master-host` must be given as a raw IP address with this binary, documented in both the Makefile comment and the standalone worker guide (`WORKER_README.md`).

**GPU worker support, added later**: `amalia_worker` gained `--gpu`/`--gpus N`, reusing the same GPU code as the main binary (one host thread per GPU, each running its own independent `WORK`→process→`RESULT` cycle against the master - the master sees this as multiple concurrent workers from one machine, no protocol change needed). Full static linking isn't possible for the GPU build - the NVIDIA driver library must stay dynamic, a hard constraint of the CUDA driver model, not a limitation of this build specifically - but everything else (CUDA runtime, glibc, libstdc++, libgomp) still links statically.

## 13. Why `a_bits=45` and not smaller: the halving/BSGS cost tradeoff, worked out precisely

Prompted by a direct question: since `tree_steps` ("halving") reduces the problem before BSGS ever runs, would reducing `a_bits` further (say, to `20`) reduce total cost, given BSGS itself would then search a smaller range per block?

**No - the opposite is true, and by a large margin.** For batched BSGS (`--block-search`-style, block size `batch_size`), the total cost to cover the whole `b`-space is:

```
blocks_needed = 2^tree_steps / batch_size
cost_per_block = √(batch_size · 2^a_bits)
total_cost = blocks_needed · cost_per_block = 2^tree_steps · √(2^a_bits) / √(batch_size)
           = 2^(root_bits - a_bits/2) / √(batch_size)          [since tree_steps = root_bits - a_bits]
```

Total cost is monotonically *decreasing* in `a_bits`, for fixed `root_bits`. Worked example, Puzzle #140 (`root_bits=140`, `batch_size=2^19`): `a_bits=20` costs `~2^130.5`; `a_bits=45` (this project's actual setting) costs `~2^117.5`; `a_bits=100` would cost `~2^90`. Reducing to `a_bits=20` from the current `45` would make the search **~5,800× more expensive**, not cheaper - confirmed both by the closed-form formula and by direct substitution of both values.

**Why**: BSGS's `√(N·R)` advantage comes specifically from searching `N` leaves and an `R`-sized `A`-range *together*, in one combined search. Every bit pushed from `a_bits` into `tree_steps` instead forces that portion of the problem into `b`-space, which is covered *linearly* (one block after another) - losing the square-root advantage for exactly the portion pushed. Taken to its limit, `a_bits = root_bits` (`tree_steps=0`, no halving at all) recovers the textbook-optimal `O(√n)` BSGS/Pollard-rho complexity exactly (`~2^70` for Puzzle #140) - confirming halving is a pure memory-management tool, never an algorithmic win, and the theoretical ceiling sits at zero tree reduction.

**So why `a_bits=45` and not higher, or zero tree reduction?** Purely a memory ceiling. Bloom1 needs the standard `~14.4` bits per element for this project's target false-positive rate (`1e-3`); at `M=2^31` (this project's setting for `a_bits=45`) that's already the measured `~3.86 GB`. Each `+5` bits of `a_bits` roughly multiplies `M`, and therefore Bloom1's size, by `32×` - `a_bits=50` would need on the order of `~124 GB`, well past a typical machine; `a_bits=55` or beyond quickly becomes impractical on any single machine regardless of CPU/GPU speed. If more RAM ever becomes available, rebuilding the hierarchy for a larger `a_bits` is a substantially larger lever than any throughput optimization elsewhere in this project.

**A related question, answered and closed in the same conversation**: could a smaller, cache-resident pre-filter checked *before* Bloom1 reduce Bloom1's own ~55-60%-of-runtime cost? No - worked out precisely: representing `M=2^31` elements at a useful false-positive rate needs the same `~14.4` bits/element regardless of where in the hierarchy the check sits; a filter small enough to fit in, say, `4MB` of cache would have roughly `0.016` bits per element - three orders of magnitude too few to filter out anything meaningful, giving a false-positive rate near `100%`. Bloom1's own prefetch is already fired for every lane in a batch before any of them is read (confirmed directly in `hierarchical_lookup`'s source, with an explanatory comment recording that a sort-for-locality variant was tried and measured `27-33%` *slower*, then reverted) - close to the best latency-hiding achievable for a multi-GB structure on real hardware. The ~55-60% is very likely close to the irreducible memory-latency floor for a table this size, not a gap left by a missing optimization.

## 14. GPU acceleration of the same Bloom1/i2/i3/exact hierarchy — a debugging-heavy investigation

The same M/M2/M3/Bloom hierarchy used by the CPU search was ported to CUDA, validated step-by-step against known-correct real data (Puzzle #64) rather than trusted from a single end-to-end run. This surfaced several real bugs, each isolated by a specific, reproducible measurement rather than by inspection alone - worth recording the diagnostic method for each, not just the fix.

**Correctness bugs** (each confirmed by comparing an intermediate value against a hand-computed or independently-known-correct one):
- A fingerprint function returning the raw high limb of a coordinate, when the CPU version applies a 3-step avalanche mix first - found by computing the expected mixed value by hand and comparing exactly against what the GPU produced.
- A missing `blockIdx.x` term in a thread-index calculation, silently making every GPU block redundantly check the same small range of points regardless of which block it actually was.
- A round-counting off-by-one from a multi-round kernel shifting a candidate point *before* checking it, rather than after - found by comparing an intermediate diagnostic dump (all of `i2`/`i3`/`idx`/`leaf_b` exactly correct) against the final reconstructed key (off by exactly one unit of `M`), isolating the bug to the round-to-candidate mapping specifically rather than the hierarchy lookup itself.
- A `--batch-size` exceeding the valid b-space for a given `tree_steps` silently producing a wrong key with the identical "off by exactly one unit of `M`" signature as the round-counting bug above - a coincidence worth noting, since it initially suggested the same root cause before the actual (parameter-validation) cause was found. Fixed by validating the batch size and refusing to run rather than risk a repeat.

**Performance investigation, in the order the bottleneck was actually chased down** (each step's finding directly motivated the next measurement, not assumed in advance):
1. A first multi-round-per-launch optimization (reducing kernel launches 256×) left measured throughput completely unchanged - the correct, important negative result that ruled out launch overhead as the bottleneck and redirected the investigation toward per-round compute cost instead.
2. Adding a shared batch-inversion across a thread block (one inversion per round, shared, instead of one per thread) gave a real ~2.2× improvement, confirming unbatched modular inversion (not launch overhead) had been the actual bottleneck.
3. A bidirectional search's `half_giant` (the round budget per search front) was found to be double what it should have been - both fronts covering the full remaining range instead of splitting it and meeting in the middle - discovered when a throughput claim based on total-time-divided-by-leaf-count turned out to be measuring a search that got lucky and stopped early, not a full exhaustive pass; recomputing from the actual number of rounds processed revealed the real (lower) throughput, which in turn led to finding the redundant-coverage bug. Fixing it gave a further ~1.8×.
4. An isolated, `cudaEvent`-timed micro-benchmark (separate from the real search binary, to exclude host-side/CPU overhead entirely) was built specifically to settle whether the remaining gap was a genuine GPU compute limitation or a measurement artifact - confirming a real, reproducible per-launch cost floor, and enabling the next finding.
5. Register-pressure-limited occupancy: `-Xptxas -v` showed 0 bytes of register spilling but 125 registers/thread, which on the specific GPU tested limits concurrent thread blocks per streaming multiprocessor to roughly 2 - with thousands of blocks needed per real search, most ran in sequential waves rather than true parallelism. Confirmed directly by comparing a single-block run (525µs) against an 8192-block run (23,447µs/round) - a ~45× difference consistent with wave-queuing, not per-block compute cost. Capping the register count via `nvcc -maxrregcount` traded some spilling for higher occupancy; sweeping values found a genuine local optimum (not a smooth curve - nearby values swung throughput by 2×+ in either direction) giving a further ~2.3× on the specific GPU tested. **Not portable across GPU generations** - the sweet spot depends on the specific SM's register budget, confirmed to need re-tuning per architecture rather than reused as a fixed default.

**A build/architecture-targeting finding, found while investigating a suspiciously slow isolated benchmark**: `nvcc` without an explicit `-arch` flag targets an old, generic default architecture, requiring the CUDA driver to JIT-compile PTX to the actual GPU's architecture on first run - a real, avoidable one-time cost, though not the dominant factor in the specific slow benchmark being investigated at the time (ruled out by testing explicitly with the correct `-arch` and finding no significant change to that specific measurement). Building with the correct `-arch` (now auto-detected from the local GPU via `nvidia-smi` at build time - see the README's Build section) avoids this JIT step regardless.

**Multi-GPU**: added by recognizing that CUDA's device context is per-host-thread, not global - a caller that calls `cudaSetDevice(i)` at the start of one host thread per GPU, before any other GPU call on that thread, gets full multi-GPU operation without any changes to the underlying kernels or search logic themselves. Applied to both the tree-based search (different GPUs claim different blocks from a shared queue, naturally load-balancing across GPUs of different speeds) and the single-target arbitrary-range search (the total lane count split into contiguous per-GPU slices, each GPU running its own independent chunk loop).
